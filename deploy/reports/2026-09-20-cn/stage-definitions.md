# 阶段定义与计时边界

[English](../2026-09-20-en/stage-definitions.md) · [实验总报告](summary.md)

本文用于解读 **2026-09-20 实验归档**，不增加任何测量结果，也不代表云端当前状态。
相关埋点代码与实验版本 `4910058` 一致。

## 最重要的区别：Agent turn 包含 Model call

**两者独立埋点，但不是互不重叠的两个阶段。** `agent` 记录核心程序处理一轮问答的
总耗时；每个 `model` 样本记录这一轮**内部**的一次聊天补全 SDK 调用。
工具执行也发生在这一轮内部，通常位于两次模型调用之间。因此：

- **不能**按 `Agent turn + Model call + KB + GitHub` 计算总时延，否则会重复计算嵌套操作。
- 一个问题可以产生多个模型调用样本。Model 行的均值/P95 是**按调用统计**，
  不是每个问题全部模型调用的总耗时。
- Agent 行包含编排和等待时间，既不是单纯的本地 Python CPU 时间，也不只是模型生成答案的时间。

### Agent turn 具体包含哪些操作？

`agent.turn` 从进入核心程序的会话轮次协调器之前开始，到响应和事件构造完成后结束，
不包含随后执行的事件输出器。其范围包括：

1. 等待并持有核心程序的会话轮次协调器，建立请求上下文，以及查询规划
   （默认规划器可以不做额外处理）。
2. 读取核心程序的会话存储。本次云端 worker 使用的是**内存中的 `BufferedSessionStore`**，
   内容来自之前加载的历史快照。
3. 准备模型消息并执行后端工具循环：一次或多次聊天补全；解析、分派模型请求的工具；
   等待检索等工具完成；将工具结果追加到消息；再次调用模型。
4. 答案后处理，包括筛选引用和组装提及对象；执行配置的答案评估器
   （默认评估器可以不做额外处理）。
5. 成功取得答案后，将用户消息和助手回复暂存到缓冲会话存储；
   后端失败时则构造兜底回复。

它**不包含**初始 HTTP 受理、外层持久化上下文/任务租约获取、worker 的归档历史读取、
历史持久化提交、首次模型/客户端组件构造、最终 Teams 格式渲染或回调发送。
核心程序内部的轮次协调器与 worker 先前获取的持久化上下文租约并不是同一层。
Agent 内部的缓冲 `session.read`/`session.write`，也不等于 Agent 外部的
`history_read`/`history_commit`。

### 本次实验中一个典型真实 Agent 问题的执行关系

```text
Agent 外部：请求受理、worker 调度/初始化、归档历史读取
Agent turn
  核心轮次协调器 -> 规划器 -> 读取缓冲会话
  后端：准备模型消息
    Model call 1：请求调用工具
    分派 search_solutions
      KB：生成 embedding -> Azure AI Search -> 过滤结果
      GitHub 实时检索（与 KB 并行）
      合并检索结果并交还后端
    Model call 2：结合工具结果生成答案
  后处理 -> 评估器 -> 写入缓冲会话
Agent 外部：渲染 -> 历史持久化提交 -> 发送最终回调
```

这是逻辑嵌套关系图，不是完整的串行执行轨迹。后端可能走其他分支或执行更多轮调用；
初始化与排队等待的观测区间也可能重叠。固定用例 `kb-01` 的样本通常有两次模型调用，
但“两次”不是协议对所有问题的保证。

例如，暖态样本组 A 有 **100 个 Agent 区间**（均值 **6,525.426 ms**）和
**200 个 Model 区间**（**每次调用**均值 **3,019.782 ms**）。
后者已经包含在前者之中：把这两个均值相加，得不到有效的单轮或完整回复时延。
同样，不能对不同分布的 P95 相加或相减，来推导另一个区间的 P95。

## 各阶段的含义

时长均为相应埋点范围内的经过时间，包含期间的等待。并非每个请求都会出现所有阶段。
空历史的真实 Agent 问题不会执行种子历史设置或合成负载。

| 报告名称 / 协议阶段名 | 计时范围 | 边界及解读注意事项 |
|---|---|---|
| 入口处理 / `ingress` | 目标宿主的 HTTP 处理器调用，直到处理器返回；包含该处理器内部的受理、鉴权、校验和持久化接收操作。 | 不包含应用处理器开始之前的平台唤醒和入站传输等时间；不等于客户端观察到的完整 ACK 时延。 |
| 受理到 worker 验证 / `queue_wait` | 从持久化的 `accepted_at` UTC 时间，到 worker 在本次尝试中首次验证并观测到该任务。 | 包含受理发布、调度、worker 初始化/验证，也可能包含先前重试等待；不是纯队列服务传输时间。可能与 `ingress`、`worker_init`、`connection` 重叠。无效或负的时钟区间会被省略，而不是改成零。 |
| Worker 对象初始化 / `worker_init` | 没有可复用 worker 时，实际执行延迟 worker 工厂构造的耗时。 | 不是容器、虚拟机或进程的完整启动时间；暖请求可能没有该观测。批量排空任务时，不会给每个任务重复计入同一初始化成本。 |
| 鉴权 / `auth` | 压测入口的 `auth.verify(headers)` 调用。 | 是入口处理的子操作，不代表系统全部 Entra/令牌操作；不包含出站回调取令牌或观察器对回调的鉴权。 |
| 延迟组件初始化 / `connection` | 已观测的宿主/客户端构造；真实 Agent 路径包括进入核心程序之前延迟创建模型和检索组件。 | 不是单独测得的 DNS、TCP/TLS 握手或 Azure 副本启动时间。宿主构造和延迟组件构造可能各自产生观测。 |
| 种子历史设置 / `history_setup` | 在 `seeded20` 模式下，读取或创建并校验确定性的种子文档，用作本问题的历史覆盖数据。 | 在核心程序执行前、Agent 外部；不是读取 20 次归档，也不是普通历史提交操作。 |
| 归档历史读取 / `history_read` | 准备新答案前，worker 从已持有租约的上下文执行 `history.get()`。 | 在 Agent 外部，不包含之前的上下文租约/投影视图获取。空历史下很小的时长，不能代表一般 Blob 读取时延。 |
| 历史持久化提交 / `history_commit` | 存在待提交历史时，在发送前为已准备好的轮次执行持久化 `history.commit(...)`。 | 在 Agent 外部，与缓冲会话写入不同；周围的任务账本/检查点更新并未全部计入该区间。 |
| 合成负载 / `synthetic` | 明确配置的压测合成操作，用于替代真实 Agent。 | 不是模型推理；不能混合统计合成负载和真实 Agent 的结果。 |
| Agent 单轮处理 / `agent` | 上文说明的完整 `agent.turn` 范围。 | 是包含聊天模型、工具、检索操作的父区间，但不包含渲染和持久化归档 I/O。 |
| KB 检索 / `kb` | 一次 `search.kb` 来源操作：查询向量生成、Azure AI Search 混合/语义检索及分页结果消费、结果过滤与转换，受检索预算约束。 | 位于 Agent 工具执行内部；包含 embedding 耗时，而 embedding **不是**聊天 `model` 区间。可能与 GitHub 检索重叠。 |
| GitHub 检索 / `github` | 一次受预算约束的 `search.github-live` 来源操作，包括等待和处理结果或失败。 | 在 Agent 内部，组合检索时与 KB 同时进行。`empty` 表示无结果，不表示 HTTP 请求失败。 |
| Web 检索 / `web` | 在配置的搜索范围/预算内，一次已观测的 `search.web` 提供商操作。 | 调用时位于 Agent 内部；多个提供商/搜索范围尝试可产生多个区间。没有观测不等于零成本或零耗时。 |
| 模型调用 / `model` | 一次包围 `chat.completions.create(...)` 的 `llm.completion`，直到响应/用量提取完成。 | 位于 Agent 内部；包含 SDK、网络、服务等待及本次 SDK 调用内的重试。不包含后续工具执行和 embedding；不是纯服务端推理时间。 |
| 渲染 / `render` | `teams.render`：把核心程序响应转换为待发送的 Teams 兼容回复结构。 | 在 Agent 返回后执行；不包含模型调用、网络发送或 Teams 客户端显示。 |
| 完整回调发送 / `send` | `benchmark.send`：发出最终回调 HTTP 请求，直到收到并验证观察器确认响应。 | 位于 Agent 外部；不包含另行埋点的回调令牌获取，也不包含 typing 发送。结束时刻可以**晚于**端到端时延使用的观察器完整正文接收时刻。 |

## 端到端时延、ACK 与证据来源

- **完整回复时延**：从提交前登记一个逻辑问题，到观察器收到完整回调正文，
  使用同一观察器进程的单调时钟计时。只有鉴权和完整消息校验通过，才接受该回复。
  这是**应用链路**测量，不是首 token 时延或 Teams 客户端显示时间。
  准备、暖身以及等待冷启动归零证明的空闲时间不计入该问题的时钟。
- **ACK 时延**：提交到受理响应的经过时间，不是完成时间。
  `202` 和 typing 事件不会释放一个未完成问题的并发槽位；有效回调也可能先于 ACK 到达。
- **完成日志**：用精确的 `job_id` **和** `trace_id` 将入口/历史/发送日志关联到回调。
  对应阶段使用日志观测替换回调观测，而不是重复累加。完整入口和发送操作可能完成得太晚，
  无法出现在原始回调快照中。
- **覆盖率与数量**：覆盖率按“具有该阶段观测的不同请求数”计算，观测数按计时区间计算。
  重试或多次调用可以增加区间数，而不增加问题数。缺失覆盖表示未知，不是零时长样本。
- **时钟边界**：本地区间使用各自的经过时间时钟；`queue_wait` 是上文特定的持久化 UTC 差值。
  不应随意相减跨进程时间戳，也不能靠累加重叠区间重建端到端时延。

本表没有分别分解平台分配、镜像启动、入站路由、独立网络握手、部分持久化租约/账本操作
及观察器工作。不能把 ACK 与入口处理的差值称为测得的纯冷启动时间。

### 模型调用数不等于模型 HTTP 尝试数

在样本组 B 中，依赖计数器 `model.calls` 记录**聊天与 embedding** 的实际 HTTP 客户端尝试，
包括 SDK 重试/重定向。而 `model_rounds` 和 `model` 时延行来自聊天补全区间。
因此，即使没有重试，两次聊天调用加一次 embedding，也可能产生
**2 个 Model 区间、3 次模型 HTTP 尝试**。
一次以 `RateLimitError` 失败的补全操作与一次 HTTP 429 尝试并不是一一对应。
尝试证据不可用时仍为未知；不能追溯性地认为较早的样本组 A 也具有这些计数器。

## 如何解读并发结果

`Concurrency = N` 表示驱动端**未完成逻辑问题数**的上限，不是 N 条 HTTP 连接、
N 次模型调用、N 个 worker 进程或 N 个 Azure 副本。
每个槽位等待最终回复/结果或截止时间，而不是只等受理 ACK。
独立会话可以并行；同一上下文的工作可能通过持久化协调串行执行。

- 成功时延分布只包含 `success`。`degraded` 表示收到完整但降级的回复；
  `failed`、投递结果 `unknown`、`expired`、`ignored` 及未完成的 `censored` 分别统计。
- **Answers/s** 是 `success + degraded` 数量除以实际测量窗口（包含排空等待）；
  **successes/s** 只用 `success` 数量除以同一窗口。
  两者都不是 HTTP ACK 吞吐量，也不是配置的并发数。
- 高负载下，仅成功样本的均值变低，可能掩盖更严重的降级或删失。
  应结合结果数量、阶段失败、依赖限流、窗口时长和副本指标一起判断。
- 本次 C4 为 76/76 成功且无降级；C16 因 `request_deadline` 停止，
  因此 C32/C64/C128 没有运行。这既不能建立 SLA，也不是平台的绝对上限。
  分钟级资源指标不是逐请求的阶段测量。
