# GitHub Copilot Advisor — 云部署与性能实验设计

> 日期:2026-09-17
> 状态:四部分设计已逐节确认;本文待用户成文审阅。
> 本文是设计,不是部署完成或性能验证报告。尚未修改运行时代码、创建实验资源或运行压测。

## 1. 目标与范围

在保留本地开发入口的基础上,增加两套可重复部署的低成本云运行方式:

- Azure Container Apps(ACA),包含常驻与允许归零两种配置。
- Azure Functions Flex Consumption,不启用 Always Ready。

部署完成后,分别输出时延、并发实验报告及成本/选型摘要。主要比较
ACA 常驻模式与 Flex 按需模式,另用 ACA 归零模式观察进一步降低闲置成本的代价。

### 1.1 已确认的边界

| 决策 | 结论 |
|---|---|
| 上云范围 | 仅 Teams 在线机器人;ingestion 保留本地 CLI,不增加云端调度 |
| 现有依赖 | 复用现有聊天、embedding、AI Search 和知识库,不复制或重建索引 |
| 区域 | 两套实验应用与状态存储均使用 Southeast Asia |
| 资源隔离 | ACA 与 Flex 各自建立实验资源组、Bot、身份和状态存储 |
| 本地开发 | 保留原启动命令与内存模式,另提供可选队列模式联调 |
| 云端处理 | 两端均采用可靠入队后确认接收、后台问答、回复原会话的流程 |
| 历史 | 消息按写入时间保存 30 天;模型仅读取该用户会话最近 20 条历史消息 |
| 认证 | Azure 依赖支持 Key/Entra;Teams 支持 client secret/托管身份 |
| 认证例外 | GitHub 保留现有 Token;Tavily、Brave 保留 Key,本次不引入 GitHub App |
| 实验目标 | 探索式测量,不预设业务时延 SLA 或某个必须达到的并发数 |
| 费用约束 | 用户不设置实验费用上限;仍按有限批次逐级加压并记录成本 |
| 部署产物 | 部署脚本、IaC、宿主配置、压测工具和报告位于 `deploy/` |

### 1.2 不在本次范围

- 改写 Agent 的回答策略、检索优先级、模型选择或人工升级逻辑。
- 新增长期记忆摘要、历史语义检索、跨会话共享记忆。
- 云端 ingestion、知识库数据迁移、生产级多区域灾备。
- 保证 Teams 发送的严格 exactly-once 或证明 Azure 平台的绝对容量上限。
- 自动更改已有本地 Bot 的消息地址,或未经确认删除现有 Azure 资源。

## 3. 方案取舍

| 方案 | 优点 | 局限 | 决策 |
|---|---|---|---|
| 双宿主+持久队列+worker | 适应长耗时问答、归零与实例回收;两端业务流程一致 | 增加队列等待、任务状态和恢复逻辑 | 采用 |
| 双宿主+HTTP 内同步问答 | 改动较少,接近当前本地流程 | 保留渠道超时与重投递风险 | 不作为云端方案 |

Azure Bot 的长任务指导指出,渠道通常只有约 10–15 秒的同步处理等待窗口。
模型问答不能依赖整个 HTTP 请求一直存活。即便采用异步流程,HTTP 入口自身的冷启动
仍可能影响接收确认,所以不能宣称队列消除了所有渠道超时。

本地直接模式继续用于快速功能验证;本地队列模式用于验证云端业务流程。
云端使用相同的任务处理语义,不将 ACA 同步路径与 Flex 异步路径混作公平对比。

## 4. 资源与组件边界

### 4.1 实验拓扑

| 资源 | ACA 环境 | Flex 环境 |
|---|---|---|
| 资源组 | `rg-copilot-advisor-aca-exp` | `rg-copilot-advisor-flex-exp` |
| 计算 | 一个 Container App:HTTP 接入+受宿主管理的 worker | 一个 Function App:HTTP Trigger+Queue Trigger |
| 状态 | 本环境独立的 Standard LRS 通用 v2 Storage | 本环境独立的 Standard LRS 通用 v2 Storage |
| Bot | 独立 F0 Azure Bot | 独立 F0 Azure Bot |
| 应用身份 | 独立用户分配托管身份 | 独立用户分配托管身份 |
| Teams 安装 | 独立实验应用包 | 独立实验应用包 |

Blob 使用 Hot 层,队列使用同一账户内的 Queue Storage。不引入常驻 Redis 或
Service Bus Premium。任务、历史、宿主文件、原始实验数据使用不同容器/队列及访问边界。
两套环境不共享会话或任务命名空间。

ACA 同时配置 HTTP 与队列缩放信号。worker 的生命周期、取消、健康检查及退出清理
由宿主管理,不是返回 HTTP 响应后遗留一个无人管理的任务。
需核验所选计费/CPU 行为能支持后台消费,并将空闲轮询开销纳入实测。

Flex 使用原生函数入口适配 SDK/应用契约,不在函数内部启动 aiohttp 监听服务,
不使用测试用 Request 对象或修改已安装 SDK 来模拟宿主。
HTTP 路径保持轻量,不为入队而初始化完整 Agent 或下载附件。

### 4.2 运行时职责

| 单元 | 单一职责 | 主要依赖 |
|---|---|---|
| 宿主入口 | 请求/响应转换、JWT 校验、协议活动路由 | Azure Functions 或 aiohttp、Agents SDK |
| 接收服务 | 消息身份/触发条件校验、可靠受理及通知 | 任务存储、会话收件箱、队列 |
| 任务存储 | 任务正文、状态、结果及幂等记录 | Blob Storage |
| 会话协调器 | 受理序号、可恢复的顺序执行、租约 | Blob Storage、队列通知 |
| 历史存储 | 30 天归档与最近 20 条上下文选择 | 内存或 Blob Storage |
| worker | 附件、既有 Agent、渲染、发送及阶段恢复 | 共享处理逻辑、Agents SDK |
| Azure 认证公共层 | 显式选择凭据及管理客户端生命周期 | Azure Identity、现有客户端 SDK |
| 实验工具 | 生成受控负载、接收测试回复、采集统计 | 独立实验身份及结果存储 |

新增共享逻辑保持现有依赖方向,不复制两份 Agent。
部署入口薄适配,业务与状态契约留在应用项目中,避免业务实现散落到部署脚本。

## 5. 消息处理与恢复

### 5.1 接收

1. 正式 `/api/messages` 保持 Azure Bot JWT 验证,校验适用的 audience、身份与消息结构。
2. 从已验证的 Teams activity 生成租户/会话/发送者分区键;缺失或冲突身份明确拒绝。
3. 保留私聊、群聊 @触发等现有规则。只有需要处理的普通消息进入后台问答队列。
4. 按分区和 activity ID 确定任务身份。先可靠保存任务与受理顺序,再可靠发送队列通知。
5. 只有受理数据和通知均可靠落地后才确认接收;失败返回明确错误。
6. 对重复投递返回已有任务的受理结果,不覆盖任务正文或重复插入会话历史。

Blob 写入和队列发送不是一个原子事务。必须有可恢复的待发送通知状态,
能处理“正文已写、通知未发”及“通知已发、确认前崩溃”。
正常重试不得让已受理任务永久失去通知,也不得插入两份逻辑任务。

`invoke`、expect-replies 等需要同步回应的活动按 SDK 协议处理,不能统一返回 `202`。
公开健康检查保持轻量;不暴露配置、依赖凭据或任务正文。

### 5.2 顺序与 worker

同一分区以服务端可靠受理序号执行,不承诺按用户客户端发送时间重排。
收件箱的短暂协调与整轮执行锁分离,上一轮长耗时问答不能长期占用接收路径的锁。
不同用户分区可以并行。

worker 取得可续期的执行租约后,处理下一条可执行任务:

1. 恢复原会话引用和消息,按需下载附件。
2. 读取本分区最新有效历史,调用现有 Agent。
3. 持久化可恢复的结果,幂等提交成功问答历史。
4. 渲染并回复原 Teams 会话/线程,记录发送结果。
5. 推进本分区序号并释放/继续处理任务,按宿主退出信号安全结束。

租约过期或续租失败必须停止后续受保护的写入/发送,不能静默继续。
已经发出的远程请求未必能撤回,恢复逻辑必须考虑这种不确定性。
锁竞争与宿主投递计数、实际业务失败次数分别记录,不能将正常争锁直接当成毒消息。

### 5.3 状态与错误

任务至少区分待通知、已排队、执行中、结果已保存、发送中、完成、
等待重试、失败、过期及发送结果不确定等状态。

- 仅对明确可重试的阶段做有界恢复,遵守服务的 Retry-After。
- 存储/通知/明确失败的发送等可恢复阶段默认最多尝试 3 次(含首次),可配置;
  正常争锁不消耗此预算。发送结果不确定时不适用自动重试。
- 不额外增加无条件重跑整轮 Agent 的重试层,保留既有模型 SDK 重试策略。
- 已保存结果的发送重试不重新调用模型,历史提交必须按任务身份幂等。
- 模型已响应但结果持久化前崩溃仍可能需要重新调用;不承诺模型费用 exactly-once。
- 发送成功但确认记录前崩溃时标记 `delivery_unknown`,不盲目重新发送。
- 授权/配置错误、非法任务及无法恢复的阶段明确终止或进入失败处理,不记成成功。
- 重试耗尽、过期与无法发送的任务保留可诊断终态;可安全通知时明确反馈用户。

错误日志只记录异常类型、阶段、允许的服务错误码/状态码及关联标识,不记录密钥、
原始 JWT、完整带凭据 URL 或任意异常正文。
清理失败也需记录,不能因为主问答完成而静默忽略。

本方案不承诺严格 exactly-once 发送。普通重复投递的幂等性与崩溃边界的不确定发送
是不同问题,实验和报告必须分别说明。

## 6. 历史保留与用户隔离

### 6.1 精确选择规则

沿用现有分区边界:

**租户 ID + 完整会话/线程 ID + 发送者 ID**。

现有 Teams 会话键使用带版本前缀的哈希表示。存储路径、协调锁、受理序号及任务幂等
必须使用相同隔离边界,不能退化为只按群或租户存储。

每次模型调用的历史读取顺序:

1. 定位当前用户会话分区。
2. 排除自写入起已经达到 30 天的消息。
3. 取此分区最近 20 条有效历史消息,按会话顺序传给模型。

20 条指历史中的用户消息与机器人对该用户的回复,通常约 10 轮成功问答;
不包含系统提示、当前问题及本轮临时工具消息。
不能先取整个群最近 20 条再过滤用户。

同群 A、B 不继承对方的问题、回答或图片解释。同一人跨租户、跨群、跨私聊、
跨频道线程也不自动共享历史。群内回复依然公开,上下文隔离不等于回复私密。

### 6.2 存储与上下文解耦

30 天是每条消息自写入开始的保留期,不是“持续活跃就不断延长所有旧消息寿命”。
超过 20 条的有效消息仍保留,只是本次不发给模型。不增加自动摘要或历史检索。

持久化层应将完整问答归档与小型最新上下文索引分离:

- 完整成功问答按任务身份幂等写入,避免每次重写全部 30 天历史。
- 最新上下文索引只维护有界窗口及必要的提交信息,常规读取不扫描完整归档。
- 历史提交与索引更新具备崩溃恢复能力,不会重复追加或暴露半轮提交。
- 读取时严格执行过期过滤;生命周期策略/清理任务最终物理删除过期对象。

逻辑过期不等于精确到秒的物理删除。若开启软删除、版本保留等额外功能,
必须另行说明实际物理保留周期与费用,不能暗中扩大保留范围。

内存模式用于开发,可以验证相同过期和窗口选择规则,但进程终止后历史仍会丢失,
不承诺跨重启保存 30 天。原启动方式保留;30 天规则替代原 1 小时规则是本次
明确确认的行为变更,不是共享存储自动产生的默认效果。

20 条上限不是 token 上限。过长输入仍可能超出模型限制;本次不额外引入 tokenizer、
自动摘要或静默截断来改变已确认的选择规则。

### 6.3 不同数据的保留期

| 数据 | 保留规则 |
|---|---|
| 成功问答历史 | 每条消息写入后 30 天 |
| 已完成任务的重复正文/临时附件引用 | 结果与历史提交完成后及时清理 |
| 失败、未完成任务正文/临时内容 | 自受理起最多 24 小时,到期进入过期处理 |
| 不含问答正文的幂等/终态元数据 | 7 天 |
| 实验原始运行数据 | 私有保存,下载/归档后可按实验清理流程删除 |

原始图片不作为长期会话记忆;保持现有的文字解释/图片标记行为。
后台下载时若附件引用已过期或下载失败,沿用明确的图片失败反馈,不能假装已看过图片。
队列只传引用,不直接塞入二进制图片、base64 大载荷或原始 JWT。

## 7. 认证与配置

| 调用面 | 兼容模式 | 云端主实验 |
|---|---|---|
| Azure OpenAI,含 chat/embedding | Key / Entra | 指定托管身份 |
| Azure AI Search | Key / Entra | 指定托管身份,运行时只读索引数据 |
| Storage 数据面 | Key / Entra | 指定托管身份,按职责授予容器/队列权限 |
| Teams/Bot 出站认证 | client secret / 用户分配托管身份 | 本环境独立 Bot 身份 |
| GitHub | 现有 Token | 不改为 Entra Token或 GitHub App |
| Tavily/Brave | Key | 保留现有配置;未配置 provider 不伪装可用 |

每种 Azure 依赖显式选择认证模式,允许渐进迁移。
本地 Entra 模式使用已登录的 Azure CLI 身份,云端使用明确指定的托管身份,
避免生产环境漫游到交互式凭据链。

选择 Entra 后即使存在旧 Key,认证失败也不得静默回退。非法模式、缺少必要配置
或权限不足需要明确报错。SDK/数据面角色与 Functions 宿主存储角色分别校验,
不能以“能部署资源”代替“可以读写数据”。

公共 Azure 凭据/客户端装配覆盖实际使用路径,包含 chat、embedding、Search 和新状态层。
若 ingestion 引用了抽取后的公共装配,保持其原本 CLI 和 Key 模式可用;
此举不将 ingestion 纳入云部署。

部署配置规则:

- 只读取 `.env` 中明确允许的变量,按数据解析,不得将内容当作 shell 脚本执行。
- 不修改用户的 `.env`,不整体上传,也不将其作为镜像构建上下文的一部分。
- Key 模式所需凭据通过宿主受保护的配置机制注入,不写入 IaC 输出、命令回显或报告。
- Entra 模式不额外复制无用的 Azure 数据面 Key。
- 现有 YAML 等运行配置也属于显式部署输入,校验路径、内容存在性及打包结果;
  缺少配置时不偷偷使用示例配置。
- 凭据、HTTP 客户端和队列消费者具有明确的启动/关闭生命周期。

实验入口与正式 Bot 入口分别鉴权。实验身份只允许提交测试命名空间任务和访问其结果,
不能任意读取其他用户历史或指定任意回复 URL。需要额外 Entra API 注册/授权时,
作为部署前置条件检查;缺少权限时请求授权,不通过放开匿名访问绕过。

## 8. 低成本配置与部署操作

### 8.1 计算与依赖成本

- ACA 起始配置为 0.25 vCPU/0.5 GiB,分别测最小副本 1 和 0。
- Flex 起始内存 512 MB,Always Ready 为 0。
- 最小规格仅是起点,不是可运行性承诺。导入、启动、代表性请求或并发下不稳定时升级,
  记录证据并对新规格重新采样,不混合不同规格结果。
- 记录最大实例数、单实例并发、worker 进程数、队列批量/轮询及缩放配置。
  这些值需满足平台当前约束与订阅配额,不能假设两个宿主参数一一等价。
- 不创建托管模型、Redis 或其他与在线部署无关的常驻服务。
- 优先复用用户明确授权的镜像仓库;无合适仓库则创建 Basic ACR。
  存在多个候选仓库时先确认目标,不自行选择无关仓库。
- 日志采用最小必要采集与明确保留设置,原始问答不作为遥测内容。

此前用户确认的 East Asia 存储报价仅用于讨论数量级:
按 Standard LRS/Hot、月平均 1 GB、每问答 5 次写入+5 次读取+10 次其他操作估算,
每套每月 1,000/10,000 次问答约为 US$0.055/US$0.334。
这不是 Southeast Asia 的报价,也不包含后来增加的队列、归档、轮询、日志或计算费用。
最终报告必须按实际区域、配置与请求量重新估算,不能沿用该值作为总费用承诺。

### 8.2 部署工具

使用 Bicep+PowerShell,保留 Python/uv 工作区及锁定依赖。

| 拟新增路径 | 职责 |
|---|---|
| `deploy/aca/` | ACA IaC、Docker 构建、部署和最小副本切换 |
| `deploy/functions/` | Flex IaC、函数宿主配置、打包和部署 |
| `deploy/shared/` | 公共部署逻辑、配置校验及安全导入 |
| `deploy/bench/` | 固定测试集、独立负载生成/测试接收器、采集统计 |
| `deploy/reports/` | 脱敏时延报告、并发报告及结论摘要 |
| `deploy/` 清理入口 | 展示并确认删除范围,清理本次资源及授权 |

运行时业务模块仍属于应用项目。打包只包含在线运行所需依赖、配置与代码,
不默认包含 ingestion、测试、开发环境、`.state`、本地凭据或整个工作区。

部署前依次检查配置、依赖、区域、配额、策略、身份和数据面权限,执行 IaC 变更预览。
明确传入已确认订阅,不能因为本机默认订阅后来改变就部署到另一个订阅。
发现同名但不属于本实验的资源时停止确认,不覆盖。

对已有 OpenAI/Search 只增加所需授权,不修改模型、索引或本地 Bot 消息地址。
需要改变现有资源认证设置等额外操作时,先展示影响并请求确认。
记录本次创建的资源和跨资源组授权,以支持精确清理。

部署脚本支持幂等重跑,失败保留真实失败状态及可恢复信息。
不把基础设施创建成功、HTTP 202 或健康检查通过等同于机器人功能通过。

## 9. 功能验证门槛

先通过本地相关单元/集成回归,再做云端功能冒烟,最后开始性能采样。
至少覆盖:

- 原本地启动方式、私聊、群 @触发、非 @消息、渲染、引用、升级和图片反馈。
- 云端 JWT 拒绝路径与同步协议活动,无效配置不能启动成匿名机器人。
- Azure 依赖 Key/Entra 两种模式、chat/embedding 同时可用、缺少权限时明确失败。
- 实际 KB 查询成功,失败/空结果/正常降级可区分,而不是知识库损坏却只靠 Web 作答。
- 相同分区连续问答顺序、跨实例重启恢复、不同用户并行与租约丢失。
- A/B/A、跨租户/群/线程/私聊、超过 20 条、恰好 30 天过期边界的组合。
- 第 21 条之后的旧消息仍在归档,但不会误入本轮模型上下文。
- 重复 activity、重复队列通知、通知前后崩溃、结果提交前后崩溃、发送不确定。
- 任务过期、有限重试、失败终态、恢复后不会重复写历史。
- 部署产物和输出不含凭据,测试入口不开放生产用户数据。

真实 Teams 验收使用两套独立实验 Bot。需要应用侧载、账号授权或客户端观察时,
请用户配合;自动化应用链路测试不能代替这一步。
未完成的真实验证项在报告中明确标注,不得复用本地旧结论宣称云端已通过。

## 10. 时延实验

### 10.1 配置矩阵

| 标识 | 配置 | 主要观察 |
|---|---|---|
| `aca-resident` | ACA 最小副本 1 | 空闲后响应、热态、负载增加时扩容 |
| `flex-on-demand` | Flex Always Ready=0 | HTTP/worker 冷启动、热态和扩容 |
| `aca-zero` | ACA 最小副本 0 | 最低闲置成本下的归零启动,作为补充 |

两端使用相同提交、Python/依赖版本、模型及版本、检索预算、工作负载和历史快照。
主比较使用托管身份;Key 模式仅做兼容验证,如另测性能则单独成组。

同区域短时压测工具与被测副本分离,负载生成和测试回复接收使用独立资源。
记录驱动端资源与饱和指标,驱动端成为瓶颈时不能归因于被测服务。
以轮换/平衡顺序运行不同宿主,不同时压同一模型争抢共享配额。

### 10.2 计时定义

分别记录接收确认、队列等待、worker 初始化、认证/首次连接、Agent、渲染和发送。
跨阶段关联包括 `trace_id`、任务标识、实例标识、启动标识、尝试次数及阶段终态,
不包含原始用户身份或问答正文。

- 单进程阶段使用单调时钟测量。
- 自动化应用链路端到端以驱动端发起请求至收到完整测试回复计时,
  起终点应使用同一观察者的单调时钟。
- 不直接相减不同进程的单调时钟;跨进程 UTC 事件仅用于关联/分段估算,
  需说明时钟误差。轮询得到的完成时间须说明轮询误差。
- 接收确认时间不能当作完整回答时间,现有 `app.startup` 也不能冒充平台冷启动。
- 自动化测试接收器替代真实 Teams 发送目的地,结果标注为应用链路时延。
  实际 Teams 客户端可见时延通过另组真实小样本观察,不与应用链路数据混称。

### 10.3 冷/热样本

归零冷启动要求有平台归零及新实例处理的正面证据,不能仅凭“等了一段时间”或日志缺失判断。
Flex 分别标记 HTTP 与队列 worker 的冷/热组合,两者可能独立扩缩。
ACA 常驻配置不归零,其部署启动、新副本启动与空闲请求不能混为同一种冷启动。

自然归零、部署/新版本启动、受控进程重启分别统计。不得先发健康检查预热,
也不得轮询被测应用的任务状态来意外保温。平台标准健康探针保留并记录。
结果观察应通过独立接收器、存储或平台遥测进行。

采样目标:

- 每个可归零配置至少 10 个已确认归零冷样本。
- 主要配置各至少 100 次热态问答;预热样本单独标记。
- 采样期间产生的新实例、重试、缓存与降级保留标签,不悄悄剔除不利样本。
- 未达到目标时报告实际样本量及原因,不以重启样本补作自然归零样本。

输出均值、P50/P95/P99、范围、样本数与失败/降级信息。
冷启动少量样本及高分位尾部统计只做探索性展示,不得包装成可靠 SLA。

## 11. 并发实验

并发定义为未达到终态的问答数。每个虚拟用户等待完整结果后才提交下一题,
不能在收到 202 后立即释放并发槽,从而把入队速率当作回答处理能力。

负载分为:

1. 合成固定任务:使用真实接入/队列/状态链路和明确标记的合成处理器,
   隔离托管及协调开销,不得称为真实模型问答能力。
2. 真实 Agent:固定的非敏感问题集,记录实际 KB/GitHub/Web 路径、模型轮次、
   token 用量、错误及降级,不假设每个问题一定走预设检索路径。
3. 一致性:同用户连续消息与多用户/会话混合,验证隔离、顺序、去重及争锁行为。

主容量测量优先使用独立用户分区,单用户串行测试另报,不能将预期的会话互斥误判为
整个平台只能串行。空历史与预置历史测试分组,预置历史长度和内容在两个宿主间一致。

阶梯为 1、2、4、8、16、32;未出现瓶颈时继续 64、128。
每档目标至少完成 50 次问答且持续不少于 3 分钟;1 并发档可复用合格的热态基线。
执行脚本显式记录观察窗口、等待期限与停止阈值,不做没有终止条件的无限压测。

初始执行参数如下,均可通过显式实验参数调整并写入运行清单:

| 参数 | 初始值/规则 |
|---|---|
| 单条问答观察期限 | 600 秒;到期仍未完成则标记为未完成/右删失,不是业务 SLA |
| 单并发档最大提交时长 | 30 分钟;达到采样目标且至少运行 3 分钟后也可结束 |
| 停止提交后的结果收集 | 最多再等待 600 秒,剩余在途任务单独列出 |
| 趋势判断窗口 | 60 秒 |
| 持续限流 | 连续两个窗口内,明确限流占该依赖已观测调用至少 5%,且每个窗口均有实际限流 |
| 持续积压 | 跳过首个升压窗口后,连续三个窗口的末尾待处理数量递增 |
| 严重宿主故障 | 出现 OOM 或非预期崩溃即停止当前档,不继续升压 |
| 单次等待自然归零 | 最多 60 分钟,超时记为未观察到归零,不伪造冷样本 |
| 每个归零配置的冷测尝试 | 最多 15 次,目标为其中至少 10 次满足冷样本条件 |

观察期限到达后不自动将仍在执行的任务当作失败回答或释放为可继续提交的正常槽位:
停止该档新增负载,进入收集/诊断。关闭相关实验资源前,对仍在途的实验任务明确决定
继续等待或取消,不得静默丢弃。若达到时间上限却不足目标样本量,报告“样本不足”。

持续依赖限流、实例崩溃或持续增长的积压触发停止升压并定位瓶颈。
尊重外部服务限流,不得通过反复重试/更换凭据绕过限制。
提前停测与观察期内未完成任务如实记录,不能当作零时延或成功回答。

每档至少报告:

- 实际实例/worker 数、规格、最大扩容配置及单实例并发设置。
- 提交量、完成量、成功/降级/失败/不确定/未完成量。
- 完整问答吞吐、队列积压/等待、均值与 P50/P95/P99。
- CPU/内存、冷启动/扩容事件、业务重试与宿主投递计数。
- 模型和外部服务限流及其对结果的影响。

成功、降级和失败时延分开解释,不能将兜底道歉或 HTTP 接收成功全部算作问答成功。
指标表注明统计窗口及分母,吞吐不混用提交速率、HTTP ACK 速率和实际完成速率。

用户未指定 SLA,因此不产生无条件的“最大支持并发数”。
结论应为“在指定规格/配置/负载与依赖配额下实测达到 C 并发、X 完整回答/秒、
对应时延及成功率”。尚未遇到瓶颈时只能声明已验证范围,不能推断平台极限。

## 12. 实验入口与报告

自动负载使用单独鉴权的实验入口,复用正式接收/协调/worker/Agent 链路,
仅测试身份和发送目的地不同。不将压测回复刷入真实群聊。
合成处理器必须显式标记且仅允许实验身份使用,不能成为生产失败的成功形态兜底。

实验模式默认关闭,仅在指定实验部署及期间启用。测试接收器地址由受控部署配置指定,
不接受请求体提供任意外部地址。实验入口的身份权限、速率和命名空间与正式 Bot 分离。

`deploy/reports/` 输出三类文档:

- 时延实验报告:环境/口径、冷启动逐样本证据、热态分布、分段耗时及限制。
- 并发实验报告:负载、实际配置、每档结果、一致性验证、瓶颈与已验证范围。
- 结论摘要:ACA 常驻/Flex 按需/ACA 归零的取舍、部署建议及成本。

每次运行保存唯一运行标识、提交与镜像/包版本、区域、模型/SKU/版本、
配置快照、测试集版本、开始/结束时间、排除样本理由与脱敏原始结果。
可提交报告不包含密钥、原始身份、聊天正文、附件或完整异常。
大体量/敏感原始产物保存在私有存储或 Git 忽略目录,不得整批加入版本库。

成本拆分为计算、镜像仓库、状态/队列操作、日志与负载生成,
另列复用服务的模型/token 与外部 API 调用增量。
区分公开单价估算与已结算/可查询费用,注明币种、区域、计费时段和账单延迟。
不将已有 Search 的固定费错误归入新增资源费,也不把归零说成零总成本。

## 13. 收尾与交付门槛

结束压测后停止提交负载,处理并记录在途实验任务,关闭实验入口,
将 ACA 恢复最小副本 0,保持 Flex 不启用 Always Ready。
保存证据后移除短时压测资源,此删除须经过明确范围确认。
常驻模式仍可通过脚本重新启用。

实验计算环境、Bot、Storage 与仓库可保留供后续使用;它们可能继续产生费用。
清理脚本必须列出具体实验资源和本次创建的跨资源组角色授权,请求确认后执行;
不得删除既有模型/Search/知识库/本地 Bot 或未归属本次实验的仓库。

实施交付至少包括:

1. 两套可重复运行的部署脚本与参数说明,部署前校验及精准清理能力。
2. 原本地启动方式、新队列模式联调说明及更新后的配置模板。
3. 两套已验证云端问答链路和 Key/Entra 兼容证据。
4. 30 天历史、最近 20 条、跨实例顺序与用户隔离的回归证据。
5. 可复现的时延/并发实验工具、实际运行结果、三类报告及限制。
6. 对仍需人工 Teams 验证、权限审批或未完成采样的事项明确列出,不宣称全部通过。

本文成文审阅通过后再编写实现计划。实现阶段按“本地回归→部署前校验→
两套云端功能验证→实验→报告/收尾”推进,不从设计审批直接跳到压测。
