# Teams 按会话与用户隔离上下文

## 1. 问题与现状

Teams 群内不同用户的提问目前会混用历史:

- `teams_adapter.extract.to_advisor_request()` 将 `conversation.id` 直接赋给
  `AdvisorRequest.conversation_key`,虽然同时提取了 `from.id`,但没有用于历史分区。
- `AdvisorCore.handle()` 按该键读取历史,成功后追加用户问题和助手回答。
- 当前提取层测试明确断言同一频道 reply thread 共享会话,没有覆盖同群不同用户。

另一个与隔离直接相关的问题是工具调用上下文:
`factory.py` 的渠道 ID 与群聊标记保存在进程级可变字典中,adapter 在调用核心前赋值。
异步问答在等待模型时可以交错,后一个请求可能覆盖前一个请求的工具参数来源。
仅修改历史键不能完成请求隔离。

当前后端每次调用都从传入历史创建本地消息列表,无需为每个用户创建独立模型客户端。
现有 `run_context.py` 已使用 `ContextVar` 保存单轮工具副作用,可沿用此模式。

## 2. 已确认的产品行为

| 项目 | 决策 |
|---|---|
| 隔离对象 | 模型历史上下文和单次请求的工具上下文 |
| 回复可见性 | 仍在原来的 Teams 群/线程中公开回复,不新增私信 |
| 历史边界 | 租户 + 会话/线程 + 用户;任何一个身份维度不同都不共享历史 |
| 同一用户跨场景 | 不跨群聊、频道线程或私聊共享历史 |
| 同一分区连续提问 | 排队处理;后一轮读取前一轮成功写入的完整问答 |
| 不同分区 | 可并行,不使用群级或进程级全局串行锁 |
| 旧群历史 | 不迁移、不回退读取,上线后从新分区的空历史开始 |
| 存储策略 | 继续使用现有内存存储、1 小时 TTL、最多 20 条消息 |
| 身份缺失 | 明确拒绝处理,不以空身份、共享键或单轮问答静默降级 |

这里的 20 条消息是现有存储上限,不是 20 组问答。TTL 仍按现有成功追加时间计算。
本设计改变主设计中“同一线程共享会话”的边界,其他会话保留策略不变。

隔离不意味着删除当前用户主动引用、粘贴的其他人文字,也不意味着群成员无法看到
已经公开发送的回答。它要求系统不自动把其他用户的历史送入本轮模型上下文。

## 3. 方案选择与范围

选择方案 A:复用现有请求契约,在 Teams 适配层生成复合历史键,
核心按键排队,工具使用请求级上下文。

备选方案:

- B:在共享请求契约中新增结构化租户、会话和隔离策略,由核心统一构造键。
  适合未来多个渠道统一身份治理,但当前没有必要扩大契约改动。
- C:为每个用户分区创建独立 Agent 实例。会增加连接、实例生命周期和回收成本,
  而现有后端已经能接受显式历史,没有必要隔离整个客户端实例。

本次不增加数据库、外部缓存、Graph 查询、成员目录权限或新依赖。
不改变模型、检索瀑布、组织级配置、用量查询的业务权限规则和公开回复方式。
不提供跨进程分布式排队、重启后历史恢复或 Teams 消息去重。
现有群级只读配置和有意共享的工具缓存不改为用户级。

## 4. 会话身份与键

### 4.1 身份来源

仅使用经现有 Teams 接入认证流程传入的 activity:

| 维度 | 字段 | 规则 |
|---|---|---|
| 租户 | `channelData.tenant.id` | 未提供时允许从 `conversation.tenantId` 读取;两处同时提供却不一致则拒绝 |
| 会话 | `conversation.id` | 保留完整值,不移除频道线程的后缀或 messageid |
| 用户 | `from.id` | 使用平台发送者 ID,不使用显示名称、正文、被 @人的 ID |

选定的三个值必须都是非空、非纯空白字符串。不把数字等类型转换成字符串,
不把格式错误的值当作缺失后继续兜底,也不修改不透明平台 ID 的原值。
不在 `from.id` 缺失时切换为 `aadObjectId`,避免同一用户因字段可用性不同而产生
两种身份来源;本次不需要跨 bot 或跨会话的用户档案。

微软文档说明 Teams `userId` 与特定 agent 和用户关联,
不能跨 agent 复用。本设计的用户键仅用于当前 bot 内部历史分区,
不把它当成全局用户账户或额外授权凭据。

### 4.2 键格式

键格式固定为 `teams:user:v1:<digest>`:

1. 依次取租户 ID、完整会话 ID、发送者 ID,构成三个字符串的 JSON 数组。
2. 序列化使用 ASCII 转义和无额外空白的分隔符,再编码为 UTF-8。
3. 对上述字节计算 SHA-256,将小写十六进制摘要接在版本前缀后。

结构化编码避免简单拼接时的分隔符歧义。键版本将新分区与旧的裸会话 ID 分开。
同一组身份的结果必须稳定,显示名称和问题正文不影响键。
哈希只用于键和日志关联中的身份最小化,不是授权判断或完全匿名化机制。

所有 Teams 场景都使用相同规则,包括个人私聊。不读取旧键,
也不尝试从没有发送者归属信息的旧历史拆分、复制消息。

### 4.3 路由与契约

`AdvisorRequest` 保留现有字段。新的值仅替换 `conversation_key`:

- `channel_id` 继续使用现有原始渠道/会话 ID,服务于渠道配置和工具路由。
- `user_id`、`user_name`、`is_group` 和图片契约保留原有语义。
- Teams 回复继续通过当前 turn context 发送,不使用历史键寻址。
- `AdvisorEvent.conversation_key` 自动记录新键;事件 schema 不变。

不新增原始用户 ID、租户 ID 或整条 activity 的日志。
现有问题摘要日志不在本次改造中扩展;其访问控制仍沿用原部署要求。

## 5. 核心处理与并发

### 5.1 每个会话键一条处理队列

每个 `AdvisorCore` 实例拥有一个 `SessionTurnCoordinator`,
由 `sessions.py` 中该 helper 维护按会话键索引的异步锁注册表,
同键请求在调用任何 planner、读取历史或生成回答前进入队列。
锁保护整个核心回合:planner、历史读取、backend、evaluator、成功历史追加和事件生成。
身份和锁键来自入口请求,不能从问题正文或模型输出推断。

成功路径仍保存用户问题和最终助手回答。下一轮获取锁后重新读取历史,
而不是复用排队前取得的历史快照。
不同会话键不共享锁,等待模型的 A 不阻塞 B 的独立问答。

队列顺序以请求进入核心并等待锁的顺序为准,不根据 Teams 客户端发送时间重排。
附件下载仍在 SDK/适配层完成,网络和下载延迟可能影响进入队列的先后。
排队保证核心处理与历史提交顺序,不新增对 Teams 网络投递/展示顺序的保证。
同一键的快速消息仍会在核心 turn 串行期间等待;本次不加 queue 深度上限,也不做 Teams 消息去重。
若平台重投递同一 activity,现阶段可能再次处理并回复。上述 queue limit 与 dedup 都不在本次修订范围内。

### 5.2 锁的生命周期

注册表记录持有者与等待者的总引用数:

- 在等待锁之前登记引用,避免等待者尚未获得锁时条目被误删。
- 正常完成、异常、等待中取消、持锁中取消都在清理路径归还引用。
- 只有没有持有者且没有等待者时才能删除条目。
- 不按 TTL 删除正在使用的锁,避免同键出现两把有效锁。

锁作用域是当前核心实例和事件循环,与现有单进程内存存储一致。
未来多实例共享历史时必须另行设计一致性与分布式协调,不能声称本方案提供这些保证。

## 6. 请求级工具上下文

移除 adapter 对两个进程级 holder 的设置职责,由核心在每轮中成对绑定请求上下文。
沿用 `run_context.py` 的 `ContextVar` 模式,使用不可变的请求路由信息保存
`channel_id` 与 `is_group`,避免单独设置产生不完整状态。

`factory.py` 的 provider 从该上下文读取当前值,`MAFBackend` 继续使用现有
provider 接口,不需要按用户创建工具或模型客户端。
在上下文未绑定时读取 provider 必须抛出明确错误,不能默认采用空渠道或私聊标记。

绑定在获得会话锁后、调用 planner 前完成,覆盖整个核心回合。
单轮 `RunContext` 在同一回合作用域内创建。回合完成、异常或取消时,
通过 token 恢复之前的请求与运行上下文,避免复用任务时遗留上一轮状态。
scope 管理职责集中在核心,adapter 不重复管理。

核心在调用 planner 前截取不可变的身份/路由字段快照。
planner 可以改写提问内容,但不得改变入口请求的会话键、渠道 ID、发送者 ID
或群聊标记。核心在 planner 返回后与该快照比较,验证这些字段未变,
既覆盖返回新对象,也覆盖对原请求的原地修改。
不允许锁保护一个分区却读写另一个分区;违反约束时明确报错,不执行模型或历史写入。

这一改造必须覆盖人工升级、网络诊断和用量查询的 provider 取值,
尤其验证群聊与私聊交错时个人用量查询的群聊限制仍然生效。
不修改这些工具既有的业务授权策略。

## 7. 错误处理

### 7.1 无法识别身份

提取层使用专门的身份校验异常报告缺失、无效或冲突的身份字段,
适配层只捕获该异常,输出固定提示:

> 无法识别本次消息的会话或用户身份,为避免混用他人的上下文,本次未处理。请重新发送;若仍失败,请联系管理员。

这条消息仍发回当前 Teams 上下文。该路径不调用核心或模型,不读写任何历史,
也不创建默认用户分区。日志记录失败类别和字段名,不记录字段值、正文或图片。
其他异常不冒充身份错误,继续由现有错误处理路径明确记录并反馈。

### 7.2 核心失败或取消

- backend 失败继续使用现有错误回复,不把失败轮次追加到成功历史。
- planner/evaluator 失败或身份约束被破坏时传播异常,由现有适配层兜底。
- 取消保持取消语义,不转换成成功响应;锁与上下文必须清理。
- 下一轮继续使用最近成功提交的历史,不永久卡在失败轮次之后。
- 不新增存储异常的静默成功兜底;未来持久化存储的原子提交另行设计。

锁保护完整问答写入不被其他回合观察到半轮状态;
本次不扩展现有 `SessionStore` 协议为分布式事务接口。

## 8. 代码与文档变更边界

以下是后续实现的职责划分,本设计提交不修改业务代码:

| 文件/区域 | 职责 |
|---|---|
| `channels/teams/src/teams_adapter/extract.py` | 身份提取/校验,唯一的 Teams 会话键构造 |
| `channels/teams/src/teams_adapter/bot.py` | 身份错误的用户反馈;移除全局 holder 设置 |
| `agent/src/advisor_agent/core.py` | 每键串行回合、请求/运行上下文作用域、planner 身份约束 |
| `agent/src/advisor_agent/sessions.py` | 提供 `SessionTurnCoordinator` 锁注册表 helper,处理每键排队和引用回收;保留存储读写协议和保留策略 |
| `agent/src/advisor_agent/run_context.py` | 请求上下文及可恢复的回合作用域,复用现有 ContextVar 模式 |
| `agent/src/advisor_agent/factory.py` | provider 读取请求上下文,去除进程级可变 holder 与过时 setter |
| 相关现有测试 | 提取层、handler、核心、上下文、装配和工具交错调用的回归测试 |
| `docs/teams-setup.md`、主设计、`docs/known-issues.md` | 更新会话边界、旧历史不继承、单进程限制和验证结果 |

保持依赖方向 `channels/teams -> agent -> shared`。共享请求/响应契约、存储协议、
模型/工具调用接口和渲染器不因本需求扩大。
不把核心或适配层变成包含无关职责的大模块。

## 9. 验收与测试

使用现有 pytest 和异步测试设施,不新增测试工具、不依赖真实 Azure/Teams 凭据。
并发测试用事件/屏障控制交错,不能靠 sleep 时长碰运气。

| 场景 | 必须验证的结果 |
|---|---|
| 同群 A -> B -> A | backend 实际收到的 B 历史不含 A 的问题/回答;A 第二轮只含自己的上一轮问答 |
| 同用户跨场景 | 群聊、其他群、频道不同线程和私聊各自独立;完整线程后缀不能被丢弃 |
| 租户隔离 | 即使会话与发送者 ID 相同,不同租户仍产生不同分区 |
| 身份稳定性 | 同组身份键稳定;改显示名称、正文不改变键;含分隔符的不同元组不产生相同编码 |
| 租户字段位置 | 两种支持的位置能正确提取;两个来源一致可接受,冲突明确拒绝 |
| 无效身份 | 对租户/会话/用户分别覆盖缺失、空白、错误类型;handler 明确回复且 core 未被调用 |
| 同键并发 | 第二轮 backend 在第一轮结束前不能开始;之后接收到第一轮完整的用户与助手消息 |
| 不同键并发 | A 被屏障阻塞时 B 能进入 backend,证明没有全局串行化 |
| 工具上下文交错 | 同时运行不同渠道的群聊和私聊,强制交错后每次实际工具调用仍收到本请求参数 |
| 群聊隐私规则 | 上述交错下,群聊的个人用量查询仍被既有规则拒绝 |
| 上下文清理 | 成功、异常和取消后都恢复外层上下文;未绑定 provider 时明确报错 |
| 锁清理 | 正常、持锁失败、等待取消、持锁取消后条目可回收且后续同键请求不死锁;有等待者时不提前删除 |
| planner 不变量 | 正常内容改写可通过;返回新对象或原地修改身份/路由均被拒绝,没有调用模型或写入错误分区 |
| 旧键不继承 | 预置旧的裸会话键历史,新用户分区的 backend 输入仍为空 |
| 既有行为 | 群 @触发、私聊触发、图片输入、引用、人工升级、TTL 与消息上限保持原行为 |

测试主要放入现有 `test_extract.py`、`test_bot.py`、`test_core.py`、
`test_sessions.py`、`test_run_context.py`、`test_factory.py` 及相关工具测试,
优先使用现有 fixture/mock 模式。群聊 fixture 须覆盖真实 `groupChat`,
不能只靠 `conversationType=channel` 的频道 fixture 代表所有群聊。
通过真实 SDK Activity 到提取函数的桥接用例验证租户字段不会在序列化时丢失。

验收以 backend 收到的真实历史参数和工具收到的实际参数为准,
不以“键不同”或“模型看起来没有串话”代替隔离断言。

## 10. 上线与人工验证

实现完成后采用新的版本化键整体切换,不保留旧的群共享模式开关。
纯内存历史在重启后本就丢失,同时仍显式禁止新路径读取旧键。
发布说明明确:正在进行的对话需要重新提供必要上下文。

在真实 Teams 中由两名用户使用非敏感、可区分的测试内容交错提问:
先让 A、B 分别提供不同的测试标记,再分别追问自己先前的标记。
确认各自能延续自己的上下文,并在另一个群/线程或私聊中不自动继承。
再验证连续提问和群聊/私聊并发;不使用真实个人资料测试隔离。

如果当前环境无法完成双账号 Teams 验证,必须明确记录尚未执行,
不能用 mock 结果声称线上隔离已验证。设计文档完成也不等于功能已实现。
